 1. TL;DR - THE 15 THINGS THAT MATTER MOST
==========================================================================================
 1. Your data follows one very simple rule [DATA][TESTED]:

        demand_kw  =  hour_level  +  8.59 x max(0, temp_C - 24)  +  random noise (std ~8.5 kW)

    hour_level is a BLOCK pattern, not a smooth curve:
        hours 00-05 : about  90 kW      hour 06    : about 133 kW
        hours 07-09 : about 174 kW      hours 10-17: about 144 kW
        hours 18-22 : about 198 kW      hour 23    : about 110 kW

 2. Humidity, solar, weekday, month, lag and rolling features add NOTHING [DATA].
    Their correlation with the leftover error is 0.00 (all between -0.012 and +0.003).

 3. So the best possible RMSE is about 8.5 kW (the noise floor). If your model gives 8.4 to 8.8
    you are at the ceiling. Do not waste days chasing 7.x. It is not there.

 4. A plain Linear / Ridge regression on 6 smart features reaches RMSE 8.5 [TESTED].
    LightGBM / XGBoost / Random Forest on the raw columns get 11 to 15 on normal validation and
    37 to 41 on a heat stress test [TESTED]. Table in section 4.5.

 5. Your test period is MUCH hotter than your training period [DATA]: average 29.2 C in the test
    file vs 18.5 C in train. Trees cannot continue a straight line past what they have seen.
    A linear model can. This is the main reason linear wins here.

 6. QuickML already has Linear Regression, Ridge, Lasso, ElasticNet and 10 more regression
    algorithms [DOC]. You do not need anything fancy inside QuickML.

 7. The key trick: build the features OUTSIDE QuickML (hour-block flags + cooling hinge) with
    ONE shared file, features.py. Use the same file in training-data prep, in predict.py and in
    the backend. Then train and inference can never disagree [TESTED].

 8. The starter test_eval.py prints SUCCESS even when your QuickML endpoint is dead, because the
    starter predict.py quietly falls back to a dummy formula [TESTED]. Do not trust SUCCESS alone.

 9. The PDF says "python predict.py --input ... --output ..." but the starter predict.py has NO
    command line. You must add it. Appendix A has a tested version.

10. Free tier = only 500 QuickML prediction calls per month [DOC]. If the endpoint takes one row
    per call, ONE run on the 1000-row sample file uses 1000 calls. Find out if batch calls work
    and ask the organizers about credits (section 18).

11. The QuickML endpoint uses Zoho OAuth. An access token lasts only 1 hour [DOC]. The judges run
    YOUR predict.py on THEIR machine. Decide now how they will authenticate (section 6.6, 18).

12. Controller rules must follow the PDF exactly. Never let battery level change the official
    mode [TESTED design]. Show battery state of charge separately.

13. In the sample test period, 67% of hours are Renewable Storage mode and 58% of hours are
    Critical Overload [TESTED]. A naive UI shows 14+ red alerts in a row. Group them into events.

14. Do NOT build LSTM / TFT / N-BEATS / foundation models. Reasons in section 15.2.

15. Work in order of score weight: (1) QuickML endpoint + predict.py, (2) live end-to-end app,
    (3) controller, (4) UI polish.

 3. TRAPS HIDDEN IN THE STARTER KIT
==========================================================================================
 T1. SILENT FALLBACK HIDES A DEAD ENDPOINT [TESTED]
     Starter predict.py: if the endpoint URL is not set OR the call fails, it prints one warning
     and returns a made-up formula. test_eval.py only checks "right length, no NaN" -> SUCCESS.
     So SUCCESS does NOT prove QuickML works. Fix: your predict.py records which source it used
     (quickml / mixed / fallback) and prints it. Always read that line before submitting.
     Also: the dummy formula scores RMSE 46 on your train data. If a judge's run falls back, you
     lose most of the 35% accuracy marks.

 T2. NO COMMAND LINE IN THE STARTER predict.py
     PDF section 8 says: python predict.py --input sample_test_input.csv --output predictions.csv
     and the output must be "timestamp,target_demand_kw", one row per input row, same order.
     Starter only has predict(input_df) and a tiny __main__ test. Add argparse. Keep the
     predict(input_df) function name and return type (numpy array) - test_eval.py imports it.

 T3. REQUEST / RESPONSE FORMAT MAY NOT MATCH
     Starter sends {"data": [rows...]} and expects {"predictions": [...]}.
     QuickML SDK docs show input as key-value pairs for ONE record and output
     {"status": "success", "result": [...]} [DOC].
     Does the REST endpoint accept many rows in one call? [TO-CHECK]. Open your endpoint
     details page: it shows the Endpoint URL, required headers and a sample request/response
     [DOC]. Match predict.py to that box. The Appendix A predict.py has 3 payload modes you can
     switch with one env var, and a parser that accepts several response shapes.

 T4. TIMEOUT = 10 SECONDS IS TOO SHORT
     A cold start can take longer. Use 30 s timeout, 3 retries with back-off, and send rows in
     chunks (default 100 per call, 4 parallel workers). [TESTED with a mock server]

 T5. AUTHENTICATION [DOC]
     Calling a published QuickML endpoint from outside needs 4 headers:
        X-QUICKML-ENDPOINT-KEY, Authorization: Zoho-oauthtoken <token>, CATALYST-ORG, Environment
     (Environment = Development or Production). Scope for the token: QuickML.deployment.READ.
     Access token lasts 1 hour. Refresh token is permanent. A refresh token can mint at most
     10 access tokens in 10 minutes, so CACHE the token (do not refresh on every call).
     India data centre token URL: https://accounts.zoho.in/oauth/v2/token [DOC].

 T6. TRAIN vs TEST TEMPERATURE SHIFT [DATA]
        Temperature band   train rows   sample-test rows
        below 10 C             828              0
        10 - 20 C            1343              1
        20 - 25 C             717            166
        25 - 28 C             436            248
        28 - 30 C             234            134
        30 - 32 C             179            165
        32 - 34 C             165            159
        above 34 C             98            127
     Test period is June-July heat. Only 98 training rows are above 34 C. Trees will be weak
     there. A straight-line (linear) cooling term is strong there.

 T7. SAMPLE TEST FILE = THE NEXT 1000 HOURS [DATA]
     train has 4000 rows (2014-12-31 23:00 to 2015-06-16 14:00). sample_test_input.csv has 1000
     rows (2015-06-16 15:00 to 2015-07-28 06:00). 4000 + 1000 = 5000 = exact 80/20 split, and the
     test starts 1 hour after train ends, no gaps. The hidden test is probably these same rows
     (targets hidden) or a similar block. Use ROW-WISE features only (no lag, no rolling), so the
     script still works if rows are shuffled, repeated or have gaps.

 T8. FREE TIER LIMITS [DOC]
     QuickML: 500 prediction calls / month, 1 GB storage, 1,800 CPU-seconds training / month.
     Price after free tier: $0.0005 per single prediction call.
     AppSail: 900 GB-minutes free per month, then $0.0013 per GB-minute.
     If any component goes over, a minimum per-project charge starts. Check billing settings.
     Plan: cache predictions, test with 24 rows, run the full 1000-row test only at the end.

 T9. OLD CATALYST SERVICES ARE DEAD [DOC]
     Catalyst File Store, Event Listeners and Cron were announced to reach end of life on
     30 April 2026. Many old tutorials still use them. Use Stratus (files), Signals (events),
     Job Scheduling (timers) instead.

 T10. QUICKML LIMITS [DOC]
     25 datasets, 25 pipelines, 10 endpoints per project. Max 25 columns in one stage operation.
     n_estimators range is 1 to 500 for ensemble models. File upload up to 1 GB.
     QuickML runs in the US, IN and EU data centres (some pages also list JP, SA, CA).

 T11. APPSAIL RULES [DOC]
     Listen on the port in env var X_ZOHO_CATALYST_LISTEN_PORT. Config file: app-config.json
     (keys: command, env_variables, memory, stack). Managed Python runtime is shown as
     Python 3.9 -> write 3.9-safe code (no match-case, no "X | Y" type hints).
     Writing files in the app folder is restricted -> use /tmp for temp files.

 T12. BROWSER TIME BUG
     Do not parse "2015-06-16 18:00:00" with new Date(). Safari can fail and other browsers
     apply the local time zone. Read the hour straight from the string (characters 11-12).
     Backend: use pandas to_datetime with NO time-zone conversion.

 T13. STARTER FILES HAVE WINDOWS LINE ENDINGS (CRLF) AND A BLANK LINE AFTER EVERY LINE
     Harmless, but clean them (dos2unix) before you commit so git diffs are readable.

 T14. SYNTHETIC-DATA QUIRKS [DATA]
     Solar is above zero at hours 03-05 and 18-19 (not realistic). The first train row is
     2014-12-31 23:00. These are just quirks of a made-up dataset. Do not try to "fix" them.

     hour:   00    01    02    03    04    05  |  06  |   07    08    09  |   10    11    12    13
     kW  :  89.1  90.1  90.8  90.0  89.6  89.9 | 132.8| 172.7 173.8 174.7| 144.7 143.8 143.0 143.8

     -> Six blocks: night(0-5)=90, 6=133, morning(7-9)=174, midday(10-17)=144, evening(18-22)=198,

     Note: the evening block 18-22 is the SAME window the controller uses for Renewable Storage.

 4.4 Cooling effect and what is left over [DATA][TESTED]
     Above 24.0 C, demand rises 8.59 kW for every 1 C. Best hinge point scanned from 18 to 30 C:
     24.0 C (RMSE 8.515 at 24.0; no better value found with 0.25 C steps).
     Slope by block: night 8.8, hour 6 9.3, morning 8.9, midday 8.7, evening 8.5, hour 23 8.0
     -> one common slope is fine. Below 24 C there is no temperature effect at all
     (Jan-Mar monthly demand is 143.7, 143.5, 143.8 while temperature rises 7 -> 17 C).
     Leftover error after the 6 hour blocks + hinge:
        std 8.52 kW; shape normal (skew 0.05, kurtosis 0.19); same size in every hour (7.6-9.4)
        and every temperature zone (7.6-8.7) -> no hidden structure.
        correlation of leftover with: humidity -0.002, solar 0.003, temp -0.001,
        temp lag 1/2/3 h -0.005/-0.005/-0.012, 3h/6h/24h average temp -0.004/-0.005/-0.007,
        heating degrees -0.004, humidity x cooling -0.002, solar lag 1h -0.002,
        previous-hour error 0.005, same-hour-yesterday error -0.008, row number -0.006.
     Day of week: mean demand 155.2 to 157.5 for all 7 days (correlation 0.000) -> ignore weekday.
     The starter's dummy cooling slope (8.5) is almost right. Its sine-wave hour pattern is wrong.
     Starter dummy RMSE on your train data: 46.09.

 4.7 Uncertainty (cheap bonus feature) [DATA][ASSUME]
     Leftover error std is 8.5 kW. So a 95% band is about +/-16.7 kW around each prediction, and
     the chance that real demand is >= 200 kW is 1 - Phi((200 - prediction) / 8.5).
     This costs no extra QuickML call. It assumes the hidden test behaves like train.

 5. MODEL PLAN (LOCAL TEST -> QUICKML -> ENDPOINT)
==========================================================================================
 5.1 Strategy in one paragraph
     Do the feature work yourself (6 numbers per row), train a LINEAR model in QuickML, publish
     it, and call it from predict.py and from the backend with the SAME features. Because the
     data is simple, a small linear model is both the most accurate and the safest in a hotter
     test period. Extra complexity gives you more risk and no gain.

 5.2 The exact features (7 columns in the training file, 25-column limit is no problem) [TESTED]
     b_night    = 1 if hour is 0..5 else 0
     b_ramp6    = 1 if hour is 6 else 0
     b_morning  = 1 if hour is 7..9 else 0
     b_evening  = 1 if hour is 18..22 else 0
     b_h23      = 1 if hour is 23 else 0
     cdd        = max(0, ambient_temp_c - 24.0)        (cooling degrees)
     (midday hours 10..17 = base level, all flags 0)   target = target_demand_kw
     Fitted on all 4000 rows (my numbers; QuickML should be very close):
        intercept 143.82 | b_night -53.91 | b_ramp6 -11.00 | b_morning +29.90
        b_evening +54.23 | b_h23 -33.86 | cdd +8.59           In-sample RMSE 8.515
     Humidity, solar and timestamp are NOT sent to the model. The UI and the SoC simulation still
     use them (solar -> PV power estimate).

 5.3 Step 0 - local check before touching QuickML (30 min)
     a) Put features.py (Appendix A) next to the CSV files.
     b) python make_train_features.py  -> creates train_features.csv (7 columns).
     c) Fit sklearn LinearRegression; confirm RMSE about 8.5 and the coefficients above.
        If you do NOT get about 8.5, stop and fix this first. QuickML will only repeat it.
     d) Keep this local model. It is your yardstick and your emergency fallback.

 5.4 Step 1 - QuickML console (names in the UI may differ a little) [DOC for the concepts]
     1. Create / open your Catalyst project in YOUR data centre (India = .in links).
     2. QuickML -> Datasets -> add data -> Local file upload -> train_features.csv (170 KB; limit 1 GB).
        Check the profile: 4000 rows, 0 nulls, all 7 columns numeric (flags must be numbers).
     3. QuickML -> Pipelines -> Create Pipeline -> type "Prediction" -> pick the dataset ->
        target column = target_demand_kw.
     4. Drag a regression node: Linear Regression (fit_intercept = True). Connect source ->
        algorithm -> destination. Save.
     5. Execute. Read the metrics: expect RMSE about 8.5 and R2 about 0.97.
     6. Publish: create an endpoint for this model version. Copy the Endpoint URL and the
        endpoint key. Note your CATALYST-ORG id and which Environment (Development/Production).
     7. Use the built-in "Test the Model" box [DOC] with the known-answer rows (Appendix B).
     8. Look at the model explanation (SHAP) chart on the endpoint page [DOC]. cdd and the evening
        flag should dominate. Screenshot it for the README and demo.
     9. Create the OAuth client (Zoho API Console of YOUR data centre, "Self Client"), scope
        QuickML.deployment.READ, exchange the code for a refresh token [DOC]. Store the client id,
        client secret and refresh token ONLY in env vars / AppSail secrets.
    10. Run the curl test in Appendix B. Confirm status 200 and the right numbers.

 5.5 Algorithm ladder (all of these exist in QuickML [DOC])
     A. Linear Regression         <- primary
     B. Ridge (alpha 0.1 to 1)     <- same accuracy, safer if you add more columns later
     C. ElasticNet (alpha 0.001..0.01) <- only if you add many extra features
     D. XGB with booster = gblinear   <- another linear option
     NOT as primary: LGBM, XGB gbtree, Random Forest, CatBoost, GB, AdaBoost, Decision Tree, KNN,
     SVM with rbf kernel. They cannot extend a straight line into hotter weather [TESTED].
     AutoML [DOC]: you may run it once as a cross-check. Judge it on the HOT part of the data,
     not on a random split. A random split can flatter tree models.
     Training budget: 1,800 CPU-seconds per month free [DOC]. Linear models use almost nothing.
     Do not run dozens of heavy tree trainings "to try".

 5.6 Validation protocol (put the numbers in your README)
     - Forward-chaining: train on the first k rows, test on the next 400 (k = 2000..3600).
     - Heat stress: train on temp <= 28 C, test on temp > 28 C.
     - Never judge only on a random split. This is time-ordered data.
     - Final model: fit on all 4000 rows.

 5.7 Acceptance numbers and the debug list
     PASS  : QuickML RMSE <= 9.0 on the same data, and the endpoint matches the known-answer
             table (Appendix B) within +/-1.5 kW.
     If QuickML RMSE is above 12, check in this order:
        1) flags uploaded as text / category instead of numbers
        2) raw "hour" (0..23) used as one number instead of flags (a straight line cannot fit blocks)
        3) cdd computed from wrong threshold or wrong unit
        4) timestamp column still in the pipeline
        5) wrong target column
        6) endpoint is serving an OLD model version (versions change when stage settings change [DOC])

 5.8 Other designs (only if Plan A fails or the organizers demand raw columns)
     - QuickML "Feature Engineering - Operations" can build features from maths on numeric columns
       [DOC]. It probably cannot do "if hour is 18..22" or max(0, x). [TO-CHECK]
     - QuickML "Custom Code" nodes (custom data transformation / ML transformation / algorithm,
       Python classes from templates) exist, but are marked "early access" [DOC]. You could put
       features.py logic inside so the endpoint takes raw timestamp + weather. More risk. Use only
       if forced.
     - Plan A (features made outside) is the simplest and it is fully under your control, because
       the judges run YOUR predict.py.

 5.9 Endpoint testing and call budget
     Every prediction call counts against the 500 free calls [DOC]. Suggested budget:
        10 calls  - curl tests (1 row, 24 rows, error cases)
        30 calls  - backend integration tests with 24-row windows
        rest      - keep for the final 1000-row run and the judges
     If one call takes many rows, great. If not, 1000 rows = 1000 calls = about $0.50 beyond the
     free tier [DOC price]. Ask organizers whether they give credits (section 18).
     Add a cache (section 6.7) so the same row never costs a second call.

 5.10 Freeze and record
     - Record: dataset version, pipeline run id, model version, endpoint key name, date.
     - A new model version is created whenever stage settings change [DOC]. After your final
       validation, do NOT edit the pipeline again unless you re-test everything.
     - Compare QuickML's coefficients (if the model page shows them) with the table in 5.2 and
       copy them into the fallback table inside predict.py, so fallback = same model.

     POST /api/forecast

 7. TRANSITION CONTROLLER + BATTERY STATE OF CHARGE
==========================================================================================
 7.1 The rules, exactly as the PDF section 6 says
        Renewable Storage Mode : demand > 160 kW   OR   hour is 18, 19, 20, 21 or 22
        Main Grid Mode         : demand <= 160 kW  AND  hour outside 18..22
        Critical Overload      : demand >= 200 kW   (independent of the mode)
     Decision table I tested (11 cases, all PASS) [TESTED]:
        demand    hour   mode                 overload
        160.00     10    MAIN_GRID            no       (> is strict)
        160.01     10    RENEWABLE_STORAGE    no
        100        17    MAIN_GRID            no
        100        18    RENEWABLE_STORAGE    no       (window start included)
        100        22    RENEWABLE_STORAGE    no       (window end included)
        100        23    MAIN_GRID            no
        150        12    MAIN_GRID            no
        199.99      3    RENEWABLE_STORAGE    no
        200.00      3    RENEWABLE_STORAGE    YES      (>= is inclusive)
        250         3    RENEWABLE_STORAGE    YES      (overload does not need the window)
        205        19    RENEWABLE_STORAGE    YES
     Notes (write them in the README):
       - Decide on the raw (unrounded) prediction. Show 2 decimals. Only a value within 0.005 kW of
         a threshold could ever differ.
       - Hour = the hour field of the timestamp. Data is hourly, so 22:00 counts and 23:00 does not.
         (A 22:30 stamp would count as hour 22. It never occurs in hourly data.)
       - Each hour is decided on its own. Do NOT add smoothing or hysteresis to the official mode.
         If you want anti-flapping, show it as a separate advisory number, not as the mode.
     "Transition signals": the PDF talks about signals when the power source changes. So also
     emit an event whenever the mode of hour t differs from hour t-1:
        "TRANSITION RENEWABLE_STORAGE -> MAIN_GRID at 2015-06-16 23:00:00"
     plus one "INITIAL STATE" signal for the first hour. Show them in the logs panel and the API.

 7.2 Battery state of charge (SoC) - the PDF gives NO formula, so these are [ASSUME] and editable
     defaults: capacity 2000 kWh, start SoC 70%, SoC limits 10%..95%, max discharge 300 kW,
     max charge 150 kW, charge and discharge efficiency 95% each, PV = 150 kWp x irradiance/1000.
     Each hour:
        pv        = pv_kwp x irradiance / 1000
        net_load  = max(0, demand - pv)         pv_surplus = max(0, pv - demand)
        RENEWABLE mode: battery_to_load = min(net_load, max discharge, usable energy x eff)
                        energy -= battery_to_load / eff ;  shortfall = net_load - battery_to_load
                        (spare PV, if any, may still charge the battery; the GRID never does)
        MAIN GRID mode: charge from pv_surplus first, then from grid, up to max charge and free
                        room;  energy += charge x eff
     GOLDEN RULE: SoC never changes the official mode. It only reports: soc_pct, shortfall_kw
     ("grid assist needed") and low_soc_warning (advisory badge). Otherwise you break the PDF rule
     and lose controller marks.
     What my test showed [TESTED]:
        Heat wave, first 72 test hours: the battery hits its 10% floor every afternoon or evening.
        At night it recharges only to about 67% by 06:00 (charge is limited to 150 kW for about
        8 hours), then drains again from 07:00. Evening shortfall (grid assist needed) is about
        200 to 290 kW. This is real behaviour of the PDF rules (67% of hours are Renewable).
        Winter day (train rows 200-223): 16 hours Main Grid, 8 hours Renewable, no overload,
        SoC moves between 43% and 95%.
     So ship two presets (heat wave and winter day) and a small settings panel for the battery.

 7.3 Alert events
     Group consecutive overload hours into ONE event: start, end, hours, peak kW. Banner text:
     "Critical overload 15:00-22:00 (8 h, peak 296 kW)". Show the biggest 3 events, then a
     "+N more" link. Use text + icon, not colour only.

 7.4 Tests to write (Appendix A has test_controller.py - I ran it)
     - the 11 boundary rows above
     - random test: for 10,000 random (demand, hour) the result equals the plain formula
     - events: grouping, one-hour event, event at the end of the window
     - battery: SoC always between limits, energy balance holds, never discharges in Main Grid
       mode, the grid never charges the battery in Renewable mode
     - API test: a 24-row request returns 24 rows, modes agree with controller, "source" present

 9. DATA INGESTION AND CLEANUP RULES
==========================================================================================
 Same rules in the UI upload, the API and predict.py (they all call features.clean_inputs).
 Check / action / message:
   Missing column            -> reject (400)  "Missing columns: [...]. Expected: timestamp, ambient_temp_c, ..."
   Header spelling/case      -> trim spaces, ignore case. Nothing else guessed.
   Timestamp format          -> accept 'YYYY-MM-DD HH:MM:SS' and ISO with 'T'. Anything else: reject with
                                an example. (Day-first dates are too risky to guess.)
   Unparsable timestamp      -> keep the row, mark it, treat hour as unknown (base level), warn.
   Not numeric (e.g. 'abc')  -> becomes missing.
   Missing numeric           -> interpolate in time order (up to 3 hours), then use safe constants
                                (temp 18.5, humidity 70, solar 0). Count it in the report.
   Out of range              -> temp [-30, 45] C, humidity [0, 100], solar [0, 1400] -> clip + warn.
                                (Train max is 38.3 C; above 45 C is a suspect sensor.)
   Duplicate timestamps      -> in the UI keep the last. In predict.py NEVER drop rows (1 output per
                                input row is a hard rule).
   Gaps / not hourly         -> warn only. Features are row-wise, so prediction still works.
   More than 24 rows         -> UI asks which 24-hour window to chart. API accepts up to 1000.
   Fewer than 24 rows        -> allowed, with a warning.
   File safety               -> max 1 MB and 1000 rows, only .csv, generated UUID object name in Stratus,
                                no user path in storage keys, parameterised / whitelisted database
                                queries, CORS allow-list, secrets only on the server.
 Return a "quality" object (rows, filled, clipped, bad_timestamp, warnings). Show it in the UI and
 write it to the logs. This is the visible proof of "clean and validate" in the PDF.

 10. predict.py, test_eval.py, README
==========================================================================================
 10.1 The contract (from the PDF and the starter test_eval.py)
      - File predict.py in the repo root, function predict(input_df) -> numpy array (or list),
        same length and same order as input rows, no NaN, no infinity.
      - Command line: python predict.py --input sample_test_input.csv --output predictions.csv
        Output file: header "timestamp,target_demand_kw", one row per input row, original timestamps.
      - test_eval.py must print SUCCESS. (It runs from the folder that holds predict.py and
        sample_test_input.csv.)

 10.2 What the Appendix A predict.py does [TESTED against a mock QuickML server, 6 scenarios]
      - cleans input (never drops a row), builds the 6 features with the shared features.py
      - sends rows in chunks (100 rows, 4 parallel workers), 30 s timeout, 3 retries with back-off
      - payload modes: data_list {"data":[rows]} (default, same as starter), list [rows], single
        (1 row per call, parallel)  -> switch with QUICKML_PAYLOAD_MODE
      - tolerant parser: {"predictions":[..]}, {"result":[..]}, list of numbers, list of dicts
      - auth modes: none (proxy or open endpoint) or oauth (4 headers, token cached 55 minutes)
      - if a chunk fails: local backup model for those rows + loud warning + LAST_RUN["source"]
        = quickml | mixed | fallback.  QUICKML_STRICT=1 turns the backup OFF (it raises instead)
      - results I saw: all 3 payload modes give identical numbers; dead endpoint + strict -> error;
        dead endpoint + not strict -> fallback flagged; shuffled rows keep the right alignment;
        a row with NaN / text / 999 C / bad timestamp still gives a finite number; 1000 rows OK.
      - RMSE of the whole path on the train rows: 8.515.

 10.3 Finish it after your endpoint exists
      1) Put your proxy URL (or endpoint URL) as the default of QUICKML_ENDPOINT_URL.
      2) Look at the endpoint's sample request/response and set QUICKML_PAYLOAD_MODE to match.
      3) Run:  QUICKML_STRICT=1 python predict.py --input sample_test_input.csv --output predictions.csv
         It must finish and print  source=quickml  failed_chunks=0.
      4) Run python test_eval.py -> SUCCESS. (Remember: SUCCESS alone proves nothing, see T1.)
      5) Compare predictions.csv with your local linear model. Max difference should be about 1.5 kW
         or less, because it is the same model.

 10.4 Pre-submission checks for predict.py
      [ ] STRICT run works and says source=quickml
      [ ] Works from a clean folder that has only the files from the repo
      [ ] Works on another laptop and another network, using only README steps
      [ ] Fresh virtual env with Python 3.9 .. 3.12 and only: numpy pandas requests
      [ ] 1000 rows finish in under 60 seconds (also after a cold start)
      [ ] No secret anywhere in predict.py, in Git history, or in the zip
      [ ] File keeps the name predict.py and the function name predict(input_df)

 10.5 README outline (judges read this first)
      1. One-paragraph summary + live URL + 3 screenshots
      2. Architecture picture and a table: Catalyst service -> what it does
      3. Model: features, why linear, local validation table (section 4.5), QuickML RMSE, SHAP picture
      4. predict.py: how to run, env vars (NAMES ONLY), payload modes, "source" line, fallback policy

      6) Signals: send an email / webhook when a new critical overload event appears.
      7) Dispatch comparison: rule-based (official) vs a simple peak-shaving plan, shown beside it.
         Keep the official rule as the main answer.
 15.2 Things NOT worth doing here
      - LSTM / GRU / TFT / N-BEATS / PatchTST: your test input has NO past demand values, so
        models that read demand history cannot run at inference. The data is "hour block +
        cooling hinge + noise", nothing for a deep net to learn. 4000 rows is small.
      - Foundation models (Chronos, TimesFM, Moirai, Time-MoE): they forecast from past values of
        the same series [PAPER]. Same problem. Not applicable.
      - Lag / rolling weather features: classic in real load forecasting [PAPER], but in your data
        they have correlation about 0.00 with the leftover error [DATA]. They only add risk if test
        rows are shuffled.
      - Tuning trees, stacking, AutoML chasing: the ceiling is 8.5. A tuned tree still loses in heat.
      - Battery reinforcement learning (pymgrid style): far too heavy, and the official mode comes
        from fixed rules anyway.
      - Smoothing the official mode: it breaks the PDF rule.
      Where these WOULD matter: real utility data, where "recency" temperature features gave 18-21%
      gains over the vanilla benchmark [PAPER]. Mention this in README under "future work".

 16. RESEARCH NOTES (PAPERS + GITHUB), WRITTEN IN MY OWN WORDS
==========================================================================================
 16.1 Load forecasting methods
  - MDPI Energies 2025, vol 18 issue 19, article 5060 (Greek power system, hourly data 2015-2024
    with temperature, humidity, holidays): LightGBM beat CNN, LSTM, GRU and CNN-LSTM on every
    metric (RMSE 101.67 MW, MAPE 1.20%, R2 0.9942). Takeaway: start with simple strong models.
  - Kazakhstan short-term load forecasting thesis (synthetic data): LightGBM and XGBoost beat
    SARIMA, LSTM and GRU; hourly pattern strong, weekly and monthly pattern weak - the same shape
    as your dataset.
  - Building thermal load study (Applied Energy 2020, LBNL): XGBoost was best among shallow models;
    LSTM only helped at 1 hour ahead, not 24 hours ahead. Takeaway: for day-ahead with weather
    inputs, simple models are enough.
  - "Tao's Vanilla Benchmark": a multiple linear regression with hour / weekday / month dummies
    and temperature terms. It is the standard yardstick in GEFCom 2012, 2014 and 2017 (HOPS paper
    arXiv 2501.10637 and others re-use it). Adding "recency" terms (lagged and averaged
    temperature, Wang-Liu-Hong 2016) improved it by 18-21% at the top level. Your solution is
    "vanilla + a cooling hinge". In your data recency terms add nothing [DATA].
  - More context: arXiv 1603.01376 (lasso for GEFCom2014), arXiv 2405.17070 (GAM mid-term), arXiv
    1901.05052 (how to choose a load-forecasting technique).
 16.2 Foundation models for load (2025-2026)
  - Meyer et al., arXiv 2410.09487 (v3 Jan 2026, IEEE Access 2025): zero-shot Chronos, TimesFM,
    Time-MoE, Sundial are about as good as transformers trained from scratch on household load.
    The paper also warns about information leakage in evaluation (a good reminder to validate by time).
  - Simeone, arXiv 2602.10848 (Feb 2026): ERCOT 2020-2024 zero-shot test. Chronos-2 gives well
    calibrated intervals (about 95% coverage at a 90% target); Moirai-2 and Prophet were
    over-confident (about 70%).
  - arXiv 2604.22077 (Apr 2026): fine-tuning foundation models helps load, solar and wind; pure
    zero-shot needs adaptation.
  Takeaway: interesting research, but all need past demand values. You do not have them. Skip.
 16.3 Microgrid and battery simulation on GitHub
  - pymgrid (Total-RD, LGPL-3.0, paper arXiv 2011.08004): Python microgrid simulator with battery,
    PV, load and generator modules. Its development moved to ahalev/python-microgrid (v1.4.1 on
    PyPI). Use it only to read how battery limits and efficiencies are modelled. It is too heavy
    for AppSail and LGPL needs care. Section 7.2 uses a tiny own model instead.

"""features.py - ONE feature definition shared by: training CSV prep, predict.py, AppSail backend.
Row-wise only (no lag / rolling), so it is safe even if test rows are shuffled or non-contiguous."""
import numpy as np
import pandas as pd

T_COOL = 24.0                      # hinge point found from data (best RMSE at 24.0 C)
FEATURE_COLS = ["b_night", "b_ramp6", "b_morning", "b_evening", "b_h23", "cdd"]   # midday = reference level
RAW_COLS = ["timestamp", "ambient_temp_c", "humidity_pct", "solar_irradiance_wm2"]


def hour_from_timestamp(ts):
    """Parse 'YYYY-MM-DD HH:MM:SS' (also ISO 'T'). Naive time, NO timezone shift."""
    return pd.to_datetime(ts, errors="coerce").dt.hour


def build_features(df):
    h = hour_from_timestamp(df["timestamp"])
    t = pd.to_numeric(df["ambient_temp_c"], errors="coerce")
    out = pd.DataFrame(index=df.index)
    out["b_night"] = ((h >= 0) & (h <= 5)).astype(float)
    out["b_ramp6"] = (h == 6).astype(float)
    out["b_morning"] = ((h >= 7) & (h <= 9)).astype(float)
    out["b_evening"] = ((h >= 18) & (h <= 22)).astype(float)
    out["b_h23"] = (h == 23).astype(float)
    out["cdd"] = np.maximum(0.0, t - T_COOL)
    return out[FEATURE_COLS]


def clean_inputs(df):
    """Validate + repair raw rows. Returns (clean_df, report). Never drops rows (1 prediction per input row)."""
    rep = {"rows": int(len(df)), "bad_timestamp": 0, "filled": {}, "clipped": {}}
    d = df.copy()
    miss = [c for c in RAW_COLS if c not in d.columns]
    if miss:
        raise ValueError("missing columns: %s" % miss)
    ts = pd.to_datetime(d["timestamp"], errors="coerce")
    rep["bad_timestamp"] = int(ts.isna().sum())
    limits = {"ambient_temp_c": (-30, 45), "humidity_pct": (0, 100), "solar_irradiance_wm2": (0, 1400)}
    for c, (lo, hi) in limits.items():
        d[c] = pd.to_numeric(d[c], errors="coerce")
        n_missing = int(d[c].isna().sum())
        if n_missing:
            d[c] = d[c].interpolate(limit_direction="both")      # neighbours in time order
            d[c] = d[c].fillna({"ambient_temp_c": 18.5, "humidity_pct": 70.0, "solar_irradiance_wm2": 0.0}[c])
            rep["filled"][c] = n_missing
        n_clip = int(((d[c] < lo) | (d[c] > hi)).sum())
        if n_clip:
            d[c] = d[c].clip(lo, hi)
            rep["clipped"][c] = n_clip
    return d, rep

"""controller.py - Section 6 rules. Mode comes ONLY from the spec rule (never from battery state)."""
import pandas as pd

RENEWABLE = "RENEWABLE_STORAGE"
MAIN = "MAIN_GRID"
DEMAND_LIMIT_KW = 160.0      # > 160  -> renewable
OVERLOAD_KW = 200.0          # >= 200 -> critical overload
PEAK_START_H, PEAK_END_H = 18, 22   # inclusive


def decide(demand_kw, hour):
    mode = RENEWABLE if (demand_kw > DEMAND_LIMIT_KW or PEAK_START_H <= hour <= PEAK_END_H) else MAIN
    return {"mode": mode, "critical_overload": bool(demand_kw >= OVERLOAD_KW),
            "reason": ("demand>160" if demand_kw > DEMAND_LIMIT_KW else "") +
                      ("+" if demand_kw > DEMAND_LIMIT_KW and PEAK_START_H <= hour <= PEAK_END_H else "") +
                      ("peak-window 18-22" if PEAK_START_H <= hour <= PEAK_END_H else "") or "demand<=160 & off-peak"}


def evaluate(timestamps, demands):
    hours = pd.to_datetime(pd.Series(list(timestamps))).dt.hour.tolist()
    return [dict(timestamp=str(t), hour=h, demand_kw=float(d), **decide(float(d), h))
            for t, h, d in zip(timestamps, hours, demands)]


def overload_events(rows):
    """Group consecutive overload hours into events (nicer banners than one alert per hour)."""
    ev, cur = [], None
    for r in rows:
        if r["critical_overload"]:
            if cur is None:
                cur = {"start": r["timestamp"], "end": r["timestamp"], "hours": 1, "peak_kw": r["demand_kw"]}
            else:
                cur["end"] = r["timestamp"]; cur["hours"] += 1; cur["peak_kw"] = max(cur["peak_kw"], r["demand_kw"])
        elif cur is not None:
            ev.append(cur); cur = None
    if cur is not None:
        ev.append(cur)
    return ev

"""battery.py - SIMULATED state of charge (spec gives no formula, so all numbers are editable assumptions).
It never changes the official grid mode; it only reports SoC + advisory flags."""
from dataclasses import dataclass


@dataclass
class BatteryParams:
    capacity_kwh: float = 2000.0
    soc_start: float = 0.70
    soc_min: float = 0.10
    soc_max: float = 0.95
    p_discharge_max_kw: float = 300.0
    p_charge_max_kw: float = 150.0
    eff_charge: float = 0.95
    eff_discharge: float = 0.95
    pv_kwp: float = 150.0          # PV power = pv_kwp * irradiance / 1000
    step_h: float = 1.0


def simulate(rows, solar, p=BatteryParams()):
    """rows: output of controller.evaluate ; solar: list of W/m2 per row. Returns rows + soc fields."""
    e = p.soc_start * p.capacity_kwh
    out = []
    for r, g in zip(rows, solar):
        pv = p.pv_kwp * max(0.0, g) / 1000.0
        d = r["demand_kw"]
        net = max(0.0, d - pv)              # load left after PV
        surplus = max(0.0, pv - d)          # PV left after load
        batt_to_load = grid_charge = pv_charge = 0.0
        room_kw = max(0.0, (p.soc_max * p.capacity_kwh - e) / (p.eff_charge * p.step_h))
        if r["mode"] == "RENEWABLE_STORAGE":
            avail_kw = max(0.0, (e - p.soc_min * p.capacity_kwh) * p.eff_discharge / p.step_h)
            batt_to_load = min(net, p.p_discharge_max_kw, avail_kw)
            e -= batt_to_load * p.step_h / p.eff_discharge
            pv_charge = min(surplus, p.p_charge_max_kw, room_kw)          # spare PV may still charge; grid may NOT
        else:
            pv_charge = min(surplus, p.p_charge_max_kw, room_kw)
            grid_charge = max(0.0, min(p.p_charge_max_kw - pv_charge, room_kw - pv_charge))
        e += (pv_charge + grid_charge) * p.step_h * p.eff_charge
        shortfall = max(0.0, net - batt_to_load) if r["mode"] == "RENEWABLE_STORAGE" else 0.0
        soc = e / p.capacity_kwh
        out.append(dict(r, pv_kw=round(pv, 1), soc_pct=round(100 * soc, 1), battery_to_load_kw=round(batt_to_load, 1),
                        grid_charge_kw=round(grid_charge, 1), pv_charge_kw=round(pv_charge, 1), shortfall_kw=round(shortfall, 1),
                        low_soc_warning=bool(soc <= p.soc_min + 0.02)))
    return out

"""predict.py - HackSphere 3.0 submission script (keeps the starter contract: predict(input_df) -> np.ndarray).

Run:  python predict.py --input sample_test_input.csv --output predictions.csv
Env vars (all optional except the endpoint URL; NEVER hard-code secrets in a public repo):
  QUICKML_ENDPOINT_URL   published endpoint URL  (or your AppSail /api/predict proxy URL)
  QUICKML_AUTH_MODE      none | oauth            (default none -> proxy or open endpoint)
  QUICKML_ENDPOINT_KEY, CATALYST_ORG, QUICKML_ENV(Development|Production)      -> headers for oauth mode
  ZOHO_CLIENT_ID, ZOHO_CLIENT_SECRET, ZOHO_REFRESH_TOKEN, ZOHO_ACCOUNTS_URL(default https://accounts.zoho.in)
  QUICKML_PAYLOAD_MODE   data_list | list | single   (default data_list = {"data":[rows]} like the starter)
  QUICKML_CHUNK (default 100), QUICKML_WORKERS (default 4), QUICKML_STRICT=1 -> no silent fallback
"""
import argparse
import os
import sys
import time

import numpy as np
import pandas as pd
import requests
from concurrent.futures import ThreadPoolExecutor

from features import FEATURE_COLS, build_features, clean_inputs

QUICKML_ENDPOINT_URL = os.getenv("QUICKML_ENDPOINT_URL", "YOUR_PUBLISHED_QUICKML_ENDPOINT_URL_HERE")
AUTH_MODE = os.getenv("QUICKML_AUTH_MODE", "none")
PAYLOAD_MODE = os.getenv("QUICKML_PAYLOAD_MODE", "data_list")
CHUNK = int(os.getenv("QUICKML_CHUNK", "100"))
WORKERS = int(os.getenv("QUICKML_WORKERS", "4"))
STRICT = os.getenv("QUICKML_STRICT", "0") == "1"
TIMEOUT_S = 30
RETRIES = 3

# Local linear model = same structure as the QuickML pipeline (fit on train_telemetry.csv). Used ONLY if the endpoint fails.
_FALLBACK_INTERCEPT = 143.82
_FALLBACK_COEF = {"b_night": -53.91, "b_ramp6": -11.00, "b_morning": 29.90, "b_evening": 54.23, "b_h23": -33.86, "cdd": 8.59}

LAST_RUN = {"source": None, "failed_chunks": 0}
_token = {"value": None, "exp": 0.0}


def _fallback(feats):
    y = np.full(len(feats), _FALLBACK_INTERCEPT, dtype=float)
    for c, w in _FALLBACK_COEF.items():
        y += w * feats[c].values
    return y


def _access_token():
    if _token["value"] and time.time() < _token["exp"]:
        return _token["value"]
    base = os.getenv("ZOHO_ACCOUNTS_URL", "https://accounts.zoho.in")
    r = requests.post(base + "/oauth/v2/token", params={
        "refresh_token": os.environ["ZOHO_REFRESH_TOKEN"], "client_id": os.environ["ZOHO_CLIENT_ID"],
        "client_secret": os.environ["ZOHO_CLIENT_SECRET"], "grant_type": "refresh_token"}, timeout=TIMEOUT_S)
    r.raise_for_status()
    _token["value"] = r.json()["access_token"]
    _token["exp"] = time.time() + 55 * 60            # tokens live 1 h; refresh early, do not refresh per call
    return _token["value"]


def _headers():
    h = {"Content-Type": "application/json"}
    if AUTH_MODE == "oauth":
        h.update({"Authorization": "Zoho-oauthtoken " + _access_token(),
                  "X-QUICKML-ENDPOINT-KEY": os.environ["QUICKML_ENDPOINT_KEY"],
                  "CATALYST-ORG": os.environ["CATALYST_ORG"],
                  "Environment": os.getenv("QUICKML_ENV", "Production")})
    return h


def _to_float(v):
    if isinstance(v, dict):                           # e.g. {"target_demand_kw": 123.4}
        v = next((x for x in v.values() if isinstance(x, (int, float, str))), None)
    return float(v)


def _extract(js, n):
    """Tolerant parser: {"predictions":[..]} | {"result":[..]} | {"status":..,"result":x} | [..]  (VERIFY on your endpoint)."""
    if isinstance(js, dict):
        js = js.get("predictions", js.get("result", js.get("data")))
    if not isinstance(js, (list, tuple)):
        js = [js]
    vals = [_to_float(v) for v in js]
    if len(vals) != n:
        raise ValueError("endpoint returned %d values for %d rows" % (len(vals), n))
    return vals


def _post(payload):
    last = None
    for k in range(RETRIES):
        try:
            r = requests.post(QUICKML_ENDPOINT_URL, json=payload, headers=_headers(), timeout=TIMEOUT_S)
            r.raise_for_status()
            return r.json()
        except Exception as e:                         # network, 4xx/5xx, bad json
            last = e
            time.sleep(2 ** k)
    raise last


def _call_chunk(records):
    if PAYLOAD_MODE == "single":
        return [_extract(_post(rec), 1)[0] for rec in records]
    payload = {"data": records} if PAYLOAD_MODE == "data_list" else records
    return _extract(_post(payload), len(records))


def predict(input_df):
    """Returns np.ndarray of predicted demand (kW), one value per input row, same order."""
    df, _ = clean_inputs(input_df.reset_index(drop=True))
    feats = build_features(df)
    n = len(feats)
    if QUICKML_ENDPOINT_URL == "YOUR_PUBLISHED_QUICKML_ENDPOINT_URL_HERE":
        if STRICT:
            raise RuntimeError("QUICKML_ENDPOINT_URL not set")
        print("WARNING: no endpoint configured -> LOCAL FALLBACK model (NOT QuickML).", file=sys.stderr)
        LAST_RUN.update(source="fallback", failed_chunks=1)
        return _fallback(feats)
    records = feats[FEATURE_COLS].to_dict(orient="records")
    chunks = [records[i:i + CHUNK] for i in range(0, n, CHUNK)]
    out, failed = [None] * len(chunks), 0

    def work(i):
        return i, _call_chunk(chunks[i])

    with ThreadPoolExecutor(max_workers=WORKERS) as ex:
        futs = [ex.submit(work, i) for i in range(len(chunks))]
        for i, f in enumerate(futs):
            try:
                idx, vals = f.result()
                out[idx] = np.array(vals, dtype=float)
            except Exception as e:
                if STRICT:
                    raise
                failed += 1
                lo = i * CHUNK
                print("WARNING: chunk %d failed (%s) -> LOCAL FALLBACK for rows %d-%d" % (i, e, lo, lo + len(chunks[i]) - 1), file=sys.stderr)
                out[i] = _fallback(feats.iloc[lo:lo + len(chunks[i])])
    LAST_RUN.update(source="quickml" if failed == 0 else ("fallback" if failed == len(chunks) else "mixed"), failed_chunks=failed)
    res = np.concatenate(out).astype(float)
    if not np.isfinite(res).all():
        raise ValueError("non-finite predictions")
    return res


if __name__ == "__main__":
    ap = argparse.ArgumentParser()
    ap.add_argument("--input", default="sample_test_input.csv")

"""Run:  python -m pytest -q test_controller.py     (or just: python test_controller.py)"""
import random
import pandas as pd
from controller import decide, evaluate, overload_events, RENEWABLE, MAIN
from battery import simulate, BatteryParams

BOUNDARY = [  # demand, hour, mode, overload
    (160.00, 10, MAIN, False), (160.01, 10, RENEWABLE, False), (100, 17, MAIN, False), (100, 18, RENEWABLE, False),
    (100, 22, RENEWABLE, False), (100, 23, MAIN, False), (150, 12, MAIN, False), (199.99, 3, RENEWABLE, False),
    (200.0, 3, RENEWABLE, True), (250, 3, RENEWABLE, True), (205, 19, RENEWABLE, True)]


def test_boundaries():
    for d, h, mode, ov in BOUNDARY:
        r = decide(d, h)
        assert (r["mode"], r["critical_overload"]) == (mode, ov), (d, h, r)


def test_random_matches_plain_formula():
    rnd = random.Random(7)
    for _ in range(10000):
        d, h = rnd.uniform(0, 400), rnd.randint(0, 23)
        r = decide(d, h)
        assert r["mode"] == (RENEWABLE if (d > 160 or 18 <= h <= 22) else MAIN)
        assert r["critical_overload"] == (d >= 200)


def test_events_grouping():
    ts = pd.date_range("2015-06-16 15:00", periods=6, freq="h").astype(str)
    rows = evaluate(list(ts), [210, 220, 150, 205, 100, 230])
    ev = overload_events(rows)
    assert [(e["hours"], round(e["peak_kw"])) for e in ev] == [(2, 220), (1, 205), (1, 230)]


def test_battery_invariants():
    rnd = random.Random(3)
    p = BatteryParams()
    ts = pd.date_range("2015-06-16 00:00", periods=24 * 14, freq="h").astype(str)
    dem = [rnd.uniform(60, 300) for _ in ts]
    sol = [rnd.uniform(0, 490) if 6 <= int(t[11:13]) <= 18 else 0.0 for t in ts]
    out = simulate(evaluate(list(ts), dem), sol, p)
    prev = p.soc_start * 100
    for r in out:
        assert p.soc_min * 100 - 0.11 <= r["soc_pct"] <= p.soc_max * 100 + 0.11, r
        if r["mode"] == MAIN:
            assert r["battery_to_load_kw"] == 0.0 and r["shortfall_kw"] == 0.0
        else:
            assert r["grid_charge_kw"] == 0.0                      # grid never charges in Renewable mode
        # energy balance (kWh): change = charge*eff - discharge/eff  (0.1 % rounding slack)
        exp = (r["grid_charge_kw"] + r["pv_charge_kw"]) * p.eff_charge - r["battery_to_load_kw"] / p.eff_discharge
        assert abs((r["soc_pct"] - prev) / 100 * p.capacity_kwh - exp) < 3.0, (r, prev)
        prev = r["soc_pct"]


if __name__ == "__main__":
    for f in (test_boundaries, test_random_matches_plain_formula, test_events_grouping, test_battery_invariants):
        f(); print("PASS", f.__name__)
